# Developer Spec-Kit --- AI 협업형 웹사이트 개발 명세

> **문서 목적**: AI 개발 에이전트가 기존 프로젝트를 안전하게
> 분석·수정하고, 일관된 품질로 구현·검증하도록 정의하는 개발 규칙\
> **기본 기술 기준**: Vanilla HTML / CSS / JavaScript\
> **적용 원칙**: 실제 저장소와 사용자 요구사항을 우선하며, 본 문서의
> 예시 구조를 무조건 강제하지 않음

------------------------------------------------------------------------

## 0. AI 개발 에이전트 공통 작업 규칙

### 0.1 요구사항 우선순위

1.  사용자의 현재 작업 지시
2.  프로젝트별 기능·화면 명세 및 승인된 디자인 레퍼런스
3.  기존 프로젝트의 구조·코딩 규칙·의존성
4.  본 Developer Spec-Kit
5.  일반적인 개발 관행

요구사항 간 충돌이 있거나 기능·데이터·보안에 영향을 주는 정보가 부족하면
임의로 확정하지 말고 질문한다. 영향이 작은 세부 사항은 합리적인 기본값을
적용하고 가정을 결과 보고에 남긴다.

### 0.2 작업 전 필수 분석

코드를 수정하기 전에 다음을 확인한다.

-   프로젝트의 실제 디렉터리 및 파일 구조
-   사용 기술, 빌드 도구, 패키지 매니저, 실행 방법
-   HTML 진입점과 CSS·JS 연결 관계
-   기존 컴포넌트, 공통 함수, 디자인 토큰
-   관련 페이지에서 사용하는 데이터와 이벤트 흐름
-   기존 코드의 변경 이력이나 사용자 제공 수정 사항(확인 가능한 경우)
-   실행·테스트 방법과 현재 오류

이미 구현된 프로젝트에서는 기존 구조를 우선 사용한다. 파일 구조를 새로
만들거나 라이브러리를 추가하기 전에 필요성과 영향 범위를 판단한다.

### 0.3 최소 변경 원칙

-   요청된 기능·페이지·섹션에 필요한 부분만 수정한다.
-   기존 동작과 스타일을 임의로 제거하거나 재작성하지 않는다.
-   전체 파일을 새로 만드는 방식은 부분 수정으로 해결할 수 없고, 사용자
    요구 또는 기술적 이유가 명확할 때만 사용한다.
-   사용하지 않는 코드 정리, 포맷 전체 변경, 파일명 변경 등 요청과
    무관한 리팩터링을 함께 수행하지 않는다.
-   기존 클래스명, ID, 데이터 속성, DOM 계층을 변경해야 한다면 참조하는
    CSS·JS와 접근성 속성을 함께 확인한다.
-   변경 전후의 기능 차이와 영향 범위를 파악한다.

### 0.4 불확실성 처리

다음은 사용자 확인 없이 임의로 결정하지 않는다.

-   프레임워크 또는 빌드 도구 도입
-   서버·DB·결제·로그인 등 외부 시스템 연동
-   유료 서비스 및 API 사용
-   기존 URL·라우팅·데이터 구조의 파괴적 변경
-   사용자 데이터 삭제 또는 저장 정책 변경
-   보안 수준에 영향을 주는 인증·권한 정책

## 1. 기술 스택 및 프로젝트 구조

### 1.1 기본 기술 원칙

-   별도 지시가 없다면 기존 프로젝트의 기술 스택을 유지한다.
-   Vanilla 프로젝트에서는 HTML5, CSS3, ES Modules 기반 JavaScript를
    기본으로 한다.
-   React, Vue, Svelte 등의 프레임워크를 임의로 도입하지 않는다.
-   외부 라이브러리는 필요한 경우에만 추가하며, 추가 이유·대안·용량 및
    유지보수 영향을 고려한다.
-   브라우저 기본 기능으로 충분히 구현할 수 있으면 불필요한 의존성을
    추가하지 않는다.
-   `type="module"`을 사용하는 프로젝트는 `file://` 직접 실행이 아닌
    로컬 개발 서버 환경을 기준으로 한다.

### 1.2 권장 디렉터리 구조

아래는 중소 규모 Vanilla 웹사이트의 예시 구조다. 실제 프로젝트 규모와
기존 구조에 맞춰 필요한 부분만 채택한다.

``` text
project/
├── index.html
├── pages/                    # 페이지가 여러 개인 경우에만 사용
│   ├── about.html
│   └── contact.html
├── assets/
│   ├── css/
│   │   ├── reset.css
│   │   ├── tokens.css
│   │   ├── global.css
│   │   ├── components.css
│   │   └── pages/
│   │       └── home.css
│   ├── js/
│   │   ├── main.js
│   │   ├── components/
│   │   ├── modules/
│   │   └── pages/
│   ├── images/
│   ├── icons/
│   └── fonts/
├── data/                     # 정적 JSON 데이터가 필요한 경우
└── README.md
```

-   작은 단일 페이지 프로젝트는 파일을 과도하게 분리하지 않는다.
-   공통으로 재사용되는 코드와 페이지 전용 코드를 구분한다.
-   실제 존재하지 않는 파일이나 폴더를 문서만 보고 가정하지 않는다.
-   경로는 프로젝트의 실제 배포 경로를 고려한다. 루트 절대
    경로(`/assets/...`)가 하위 경로 배포에서 문제를 일으키는지 확인한다.

### 1.3 파일 책임

  영역               책임
  ------------------ -------------------------------------
  HTML               콘텐츠 구조, 의미 요소, 접근성 속성
  tokens.css         공통 디자인 토큰
  global.css         기본 스타일, 레이아웃 공통 규칙
  components.css     재사용 컴포넌트
  pages/\*.css       페이지 전용 스타일
  components/\*.js   재사용 가능한 UI 동작
  modules/\*.js      데이터 처리, 저장, API 등 기능 모듈
  pages/\*.js        페이지별 초기화 및 화면 로직
  main.js            애플리케이션 진입 및 공통 초기화

## 2. HTML / CSS 개발 규칙

### 2.1 HTML

-   HTML5 시맨틱 요소를 목적에 맞게 사용한다.
-   제목은 문서 구조에 맞는 계층으로 작성한다.
-   버튼은 동작에, 링크는 이동에 사용한다. 클릭 이벤트를 위해 의미 없는
    `div`를 사용하지 않는다.
-   폼 컨트롤은 레이블과 연결하고 오류 메시지를 프로그램적으로 연결한다.
-   이미지에는 정보 전달 여부에 따라 적절한 `alt`를 작성한다. 장식
    이미지는 `alt=""`를 사용한다.
-   반복 요소는 고유하고 안정적인 식별 기준을 갖도록 한다.
-   의미 없는 `div` 중첩과 불필요한 ARIA 속성을 지양한다.

### 2.2 CSS

-   공통 값은 디자인 토큰을 사용한다.
-   클래스명은 기존 프로젝트의 규칙을 우선한다. 신규 작성 시 BEM 또는
    프로젝트에서 일관되게 사용하는 명명법을 따른다.
-   상태는 `.is-active`, `.is-open`, `.is-disabled` 등 의미 있는 상태
    클래스로 표현할 수 있다.
-   모든 인라인 스타일 조작을 금지하지는 않는다. 동적으로 계산되는
    값이나 CSS 변수 전달 등 적절한 경우에는 허용하되, 상태 표현은 클래스
    기반을 우선한다.
-   `!important`는 불가피한 경우에만 제한적으로 사용하고 이유를 남긴다.
-   고정 높이로 콘텐츠를 자르지 말고 콘텐츠 길이와 반응형을 고려한다.
-   `position: absolute`는 장식·오버레이 등 목적이 분명한 경우에
    사용한다.
-   `overflow: hidden`으로 문제를 감추지 말고 실제 원인을 해결한다.
-   전역 선택자와 과도하게 높은 선택자 우선순위를 피한다.

### 2.3 반응형

-   모바일 우선 또는 데스크톱 우선 중 기존 프로젝트의 패턴을 유지한다.
-   브레이크포인트는 디자인 레퍼런스와 콘텐츠가 무너지는 지점을 기준으로
    정한다.
-   고정 폭·고정 위치를 남용하지 않고 유동 레이아웃을 우선한다.
-   화면 크기 변경 시 이미지 비율, 텍스트 줄바꿈, 버튼 터치 영역, 메뉴
    전환을 검증한다.
-   가로 스크롤이 의도된 요소가 아니라면 문서 전체의 수평 오버플로를
    제거한다.
-   미디어쿼리를 추가할 때 기존 규칙과 중복·충돌하는지 확인한다.

## 3. JavaScript 모듈 및 상태 관리

### 3.1 기본 원칙

-   ES Modules를 사용하고 모듈 간 책임을 명확히 분리한다.
-   전역 변수와 전역 함수의 무분별한 사용을 피한다.
-   DOM 접근은 필요한 시점에 수행하고, 요소가 없는 페이지에서 오류가
    발생하지 않도록 한다.
-   페이지별 스크립트는 해당 페이지에서만 초기화되도록 구성한다.
-   상태 관리 라이브러리나 자체 Store는 실제 복잡도가 필요성을 뒷받침할
    때만 도입한다.
-   단순한 UI 상태는 컴포넌트 내부 변수와 DOM 상태로 충분히 관리할 수
    있다.

### 3.2 상태 관리 선택 기준

  복잡도                               권장 방식
  ------------------------------------ --------------------------------
  단일 컴포넌트 내부 상태              모듈 내부 변수 및 함수
  여러 컴포넌트가 공유하는 작은 상태   공통 모듈 또는 CustomEvent
  여러 화면에서 지속되는 상태          명시적 Store + 저장 계층
  서버 데이터 및 동기화                API 계층과 로딩·오류 상태 분리

자체 Store를 도입할 경우 다음을 정의한다.

-   상태 변경의 단일 진입점
-   구독 등록 및 해제
-   변경 감지 범위(중첩 객체·배열 포함 여부)
-   불변성 또는 변경 가능성 정책
-   저장소 동기화 실패 처리
-   초기 데이터 검증 및 버전 관리
-   여러 탭 간 동기화 필요 여부

단순한 `Proxy`는 중첩 객체의 변경을 자동 감지하지 못한다. 배열·중첩
객체를 포함하는 상태를 다룰 때는 불변 업데이트를 명시적으로 적용하거나
검증된 상태 관리 방식을 사용한다.

### 3.3 Store 구현 예시(얕은 상태 전용)

아래 코드는 최상위 속성 변경만 감지하는 최소 예시다. 중첩 객체의 내부
변경은 감지하지 않는다.

``` javascript
export class Store {
  #state;
  #listeners = new Set();

  constructor(initialState = {}) {
    this.#state = { ...initialState };
  }

  getState() {
    return this.#state;
  }

  setState(partialState) {
    const nextState = { ...this.#state, ...partialState };
    const changed = Object.keys(nextState).some(
      key => !Object.is(this.#state[key], nextState[key])
    );

    if (!changed) return;

    this.#state = nextState;
    this.#listeners.forEach(listener => {
      listener(this.#state);
    });
  }

  subscribe(listener) {
    this.#listeners.add(listener);
    return () => this.#listeners.delete(listener);
  }
}
```

이 예시는 중첩 상태를 직접 수정하지 않고 새 객체로 교체하는 사용을
전제로 한다. 프로젝트에 필요하지 않다면 Store 자체를 구현하지 않는다.

## 4. 데이터 저장 및 API 연동

### 4.1 LocalStorage / SessionStorage

-   저장 데이터는 JSON 직렬화·역직렬화 오류를 처리한다.
-   저장소 접근이 차단되거나 용량이 초과될 수 있음을 고려한다.
-   저장 데이터는 사용자 입력 또는 오래된 버전일 수 있으므로 읽을 때
    유효성을 검증한다.
-   민감한 개인정보, 인증 토큰, 결제 정보 등을 LocalStorage에 저장하지
    않는다.
-   저장 데이터 구조가 변경되면 버전 키 또는 마이그레이션 전략을
    적용한다.
-   저장소 값이 없거나 손상된 경우 안전한 기본값으로 복구한다.

### 4.2 API

-   API 호출은 화면 로직과 분리한다.
-   HTTP 오류, 네트워크 오류, JSON 파싱 오류를 구분해 처리한다.
-   로딩·성공·빈 결과·오류 상태를 UI에 반영한다.
-   중복 요청 방지, 요청 취소(AbortController), 타임아웃이 필요한지
    검토한다.
-   인증 정보와 비밀 키를 프론트엔드 코드에 하드코딩하지 않는다.
-   실제 서버 연동이 없는 경우 Mock 데이터를 실제 API인 것처럼 표현하지
    않는다. Mock 사용 범위와 교체 지점을 명확히 표시한다.

## 5. 이벤트 및 DOM 처리

### 5.1 이벤트 리스너

동적으로 생성되는 반복 요소에 이벤트를 연결해야 하는 경우 Event
Delegation을 고려한다. 단, 모든 이벤트 리스너를 금지하는 것은 아니다.
컴포넌트 초기화 시 한 번 등록하는 개별 이벤트는 허용한다.

``` javascript
const productGrid = document.querySelector("#product-grid");

productGrid?.addEventListener("click", event => {
  const button = event.target.closest('[data-action="add-to-cart"]');

  if (!button || !productGrid.contains(button)) return;

  const productId = button.dataset.productId;
  if (!productId) return;

  // 해당 상품의 동작 실행
});
```

-   이벤트 리스너가 반복 등록되지 않도록 초기화 흐름을 관리한다.
-   컴포넌트 제거 또는 재초기화 시 필요하면 리스너를 해제한다.
-   `event.target`이 텍스트 노드 또는 하위 아이콘일 수 있으므로
    `closest()` 사용 시 안전성을 확인한다.
-   비동기 이벤트 처리에서 중복 실행과 오류를 처리한다.

### 5.2 DOM 업데이트

-   텍스트 출력은 가능한 한 `textContent`를 사용한다.
-   HTML 문자열을 삽입해야 한다면 신뢰할 수 있는 템플릿만 사용하고
    사용자 입력을 그대로 삽입하지 않는다.
-   DOM 업데이트를 위해 `innerHTML`을 사용할 경우 XSS 위험을 검토한다.
-   반복 렌더링은 필요한 영역만 갱신하고 전체 문서를 불필요하게
    재생성하지 않는다.

## 6. 보안 규칙

### 6.1 XSS 방지

가장 안전한 기본 방식은 텍스트를 `textContent`로 삽입하는 것이다.

``` javascript
element.textContent = untrustedText;
```

HTML 문자열을 반드시 만들어야 하는 경우에만 상황에 맞는 검증된
Sanitizer를 사용한다. 단순한 HTML escaping 함수는 HTML 본문 텍스트
문맥에만 제한적으로 사용할 수 있으며, 속성·URL·JavaScript·CSS 문맥을
안전하게 만들지는 않는다.

``` javascript
export function escapeHTMLText(value = "") {
  return String(value).replace(/[&<>"']/g, char => ({
    "&": "&amp;",
    "<": "&lt;",
    ">": "&gt;",
    '"': "&quot;",
    "'": "&#39;"
  })[char]);
}
```

-   `href`·`src`에 외부 입력을 넣을 때 허용 프로토콜과 출처를 검증한다.
-   `javascript:` 등 위험한 URL 스킴을 허용하지 않는다.
-   사용자 입력을 `eval`, `new Function`, 인라인 이벤트 핸들러에
    전달하지 않는다.
-   인증·권한 검증은 프론트엔드 UI만으로 구현하지 않는다. 서버에서
    검증해야 한다.

### 6.2 기타 보안

-   API 키·비밀 키·비밀번호를 저장소나 클라이언트 번들에 포함하지
    않는다.
-   외부 링크에 새 창 열기를 사용할 경우 `rel="noopener noreferrer"`를
    검토한다.
-   파일 업로드가 있다면 파일 형식·크기·실제 콘텐츠 검증을 서버 측에서도
    수행한다.
-   보안 관련 요구사항이 있으면 구현 범위와 서버 측 책임을 분리해
    명시한다.

## 7. 성능 및 안정성

1.  이미지에는 실제 비율을 반영한 `width`·`height` 또는 `aspect-ratio`를
    지정한다.
2.  첫 화면의 주요 이미지에는 무조건 `loading="lazy"`를 적용하지 않는다.
    화면 아래 이미지에 지연 로딩을 적용한다.
3.  이미지에는 상황에 따라 `decoding="async"`를 적용한다.
4.  이미지 형식(WebP, AVIF 등)은 브라우저 지원과 원본 자산 제공 여부를
    고려한다.
5.  검색 입력은 일반적으로 200\~400ms debounce를 고려한다.
6.  Scroll / Resize 이벤트는 실제 성능 문제가 있는 경우 throttle 또는
    `requestAnimationFrame` 기반 처리를 검토한다.
7.  이벤트 리스너, 타이머, Observer는 더 이상 필요하지 않을 때 정리한다.
8.  DOM 측정과 스타일 변경을 반복해 레이아웃 스래싱을 일으키지 않는다.
9.  무거운 라이브러리와 불필요한 애니메이션을 피한다.
10. 성능 개선은 측정 가능한 문제를 기준으로 진행하며 근거 없는 최적화를
    하지 않는다.

## 8. 접근성 및 사용성

-   키보드만으로 주요 기능을 이용할 수 있어야 한다.
-   포커스 표시를 제거하지 않는다.
-   버튼과 링크의 의미를 구분한다.
-   Drawer·Modal·모바일 메뉴는 포커스 이동과 복귀, Escape 닫기 등을
    구현한다.
-   동적 상태 메시지는 필요한 경우 `aria-live`를 사용한다.
-   폼 오류는 텍스트로 설명하고 해당 입력과 연결한다.
-   `prefers-reduced-motion`을 존중한다.
-   HTML 기본 시맨틱을 우선하고 ARIA는 필요한 경우에만 사용한다.

## 9. 오류 처리 및 코드 품질

-   콘솔 오류와 경고를 방치하지 않는다.
-   DOM 요소가 없는 경우의 예외를 고려한다.
-   사용자에게 노출되는 오류 메시지는 이해하기 쉬운 언어로 작성한다.
-   내부 오류 정보, 토큰, 개인정보를 사용자 화면에 노출하지 않는다.
-   함수는 하나의 책임을 갖도록 구성하고, 이름은 역할을 명확히 표현한다.
-   불필요한 추상화, 과도한 클래스 계층, 사용하지 않는 유틸리티를 만들지
    않는다.
-   기존 코드 스타일과 포맷 규칙을 우선한다.

## 10. 테스트 및 완료 기준

### 10.1 기본 검증

작업 완료 전 최소한 다음을 수행한다.

-   [ ] 변경 파일과 변경 범위 확인
-   [ ] HTML·CSS·JS 문법 및 경로 오류 확인
-   [ ] 브라우저 콘솔 오류 확인
-   [ ] 요청된 기능의 정상 동작 확인
-   [ ] 주요 예외 상태(빈 값, 잘못된 입력, 네트워크 실패 등) 확인
-   [ ] PC·태블릿·모바일 주요 뷰포트 확인
-   [ ] 가로 스크롤, 겹침, 잘림, 이미지 비율 확인
-   [ ] 키보드 탐색 및 포커스 확인
-   [ ] 기존 기능이 회귀하지 않았는지 확인

### 10.2 브라우저 검증 폭

최소 권장 폭: 360px, 390px, 768px, 1024px, 1280px, 1440px.\
프로젝트 요구사항에 별도 기기 또는 브라우저가 있으면 해당 환경을
추가한다.

### 10.3 완료 조건

다음 조건을 충족해야 완료로 보고한다.

-   사용자 요구사항을 구현했거나 미구현 항목을 명시했다.
-   관련 페이지에서 기능과 레이아웃을 검증했다.
-   기존 기능에 영향을 준 변경이 있다면 그 내용을 설명했다.
-   검증하지 못한 항목은 검증 완료로 표시하지 않았다.
-   실행 방법 또는 테스트 방법이 변경되었다면 문서화했다.

## 11. AI 작업 절차

AI 에이전트는 다음 순서로 작업한다.

1.  **요구사항 파악**: 목표, 수정 범위, 완료 조건, 레퍼런스를 정리한다.
2.  **프로젝트 분석**: 파일 구조, 기존 코드, 의존성, 관련 페이지를
    확인한다.
3.  **영향 범위 판단**: 수정할 파일과 기존 동작에 미칠 영향을 정리한다.
4.  **구현 계획**: 필요한 변경만 단계별로 계획한다. 큰 구조 변경은 먼저
    사용자 승인을 받는다.
5.  **구현**: 기존 규칙과 디자인 명세를 따르며 최소 범위로 수정한다.
6.  **검증**: 기능·반응형·접근성·콘솔 오류를 확인한다.
7.  **결과 보고**: 수정 파일, 구현 내용, 검증 결과, 미해결 이슈를
    보고한다.

### 11.1 작업 결과 보고 형식

``` text
[작업 결과]
- 작업 목표:
- 수정 파일:
- 주요 변경 사항:
- 유지한 기존 기능:
- 검증 환경 및 뷰포트:
- 검증 결과:
- 미해결 이슈 / 추가 확인 필요 사항:
- 실행 또는 확인 방법:
```

### 11.2 금지 사항

-   사용자 승인 없이 프레임워크·빌드 도구·주요 라이브러리를 교체하지
    않는다.
-   요청하지 않은 페이지나 기능을 임의로 수정하지 않는다.
-   레퍼런스의 콘텐츠·이미지·레이아웃을 임의로 생략하거나 대체하지
    않는다.
-   검증하지 않은 기능을 정상 동작한다고 단정하지 않는다.
-   실제 연동되지 않은 기능을 완료된 기능처럼 표시하지 않는다.
-   오류를 숨기기 위해 `overflow: hidden`, 무분별한 `!important`, 빈
    예외 처리 등을 사용하지 않는다.
